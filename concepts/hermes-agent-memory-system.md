# Hermes Agent 记忆系统机制

## 概述

Hermes Agent 的记忆/上下文系统由**三层独立机制**构成，各有不同的作用范围、加载时机和 token 成本。理解这三层的差异是高效使用 Agent 的关键。

---

## 三层架构

### 1. 持久记忆 —— `memory` 工具

| 属性 | 说明 |
|------|------|
| 存储方式 | 两条独立记录：`MEMORY`（环境笔记）和 `USER`（用户档案） |
| 注入时机 | **每次对话每条消息**都自动拼入系统提示词 |
| 容量上限 | **2,200 字符**（两条共享） |
| 更新方式 | 主动调用 `memory(action='add/replace/remove')` |
| 适用场景 | 环境事实（OS、硬件）、用户偏好、工具限制、项目路径等**稳定不变的上下文** |

**特点**：高可见性（永远在上下文中），但空间有限，且所有条目不论是否相关都消耗 token。

### 2. 会话搜索 —— `session_search` 工具

| 属性 | 说明 |
|------|------|
| 存储方式 | SQLite 全文索引（FTS5），存所有历史消息 |
| 加载时机 | **Agent 主动调用**，不自动注入 |
| 搜索方式 | FTS5 **关键词匹配**（非语义搜索），默认 AND 逻辑 |
| 返回数量 | 默认 Top 3 条匹配会话 |
| 适用场景 | 回溯具体讨论内容、定位过去的对话 |

**局限性**：
- **不是语义搜索**——用词不同就搜不到（"宝塔面板" vs "建站工具"）
- **只返回 Top N**——跨天会话易被埋没
- **无日期感知**——不按时间排序，只按关键词匹配度
- **每次调用消耗 token 和延迟**——不能每个问题都搜

### 3. 技能 —— `skill` 系统

| 属性 | 说明 |
|------|------|
| 存储方式 | 本地 `SKILL.md` 文件，可选推送到 GitHub 仓库 |
| 加载时机 | Agent 判断任务相关时**按需加载**（用 `skill_view()` 读取） |
| 容量 | 不限（本地文件） |
| 适用场景 | 操作步骤、最佳实践、踩坑记录、方法论等**可复用的流程知识** |

## 单槽轮换摘要方案

### 为什么需要

`session_search` 有时会搜不到（用词差异），而 `memory` 空间有限，堆太多历史条目会填满空间且浪费 token。

### 方案

只在 memory 里保留 **1 条**「上次会话摘要」，固定位置，每次覆盖更新：

```
上次会话摘要: [日期] [主题] - [关键结论/状态]
```

### 对比

| | 完整记忆历史 | session_search | 单槽轮换摘要 |
|---|---|---|---|
| **每次 token 成本** | 每次均携带，随条目增长 | 仅搜索时产生 | 约 100 字 / 25-35 tokens，固定不变 |
| **跨日连续性** | ✅ 能存多条 | ❌ 需主动搜索、可能漏 | ✅ 看一眼就知道上次在干嘛 |
| **回溯深度** | ❌ 2,200 上限 | ✅ 不限量，搜到就有 | ❌ 只存上次，更早需 session_search |
| **维护成本** | ❌ 需定期整理 | ✅ 零维护 | ✅ 自动覆盖 |

### 执行规则

- **何时更新**：每次完成「复杂任务」后覆盖更新（5+ 工具调用、有结论的项目、用户说"下一个"时）
- **不更新**：日常闲聊、一问一答小问题、无结论的中间步骤
- **格式**：`上次会话摘要: [日期] [主题] - 一句话结论/状态`
- **回溯更早记录**：仍通过 `session_search` 查询

## 决策建议

| 场景 | 用哪个 |
|------|--------|
| 每次对话都要知道的环境信息 | → `memory`（自动注入） |
| 上次聊了什么/中断在哪 | → 看 `memory` 里的「上次会话摘要」 |
| 更早的某次具体讨论 | → `session_search`（关键词搜） |
| 某个任务怎么做的完整步骤 | → `skill`（按需加载） |
