## AI #3

# 一、先分清：JWT 三部分 哪段是明文、哪段是哈希签名
JWT 格式固定：
```
Header . Payload . Signature
```

### 1. Header 头部
**Base64编码明文**
不是加密、不是哈希，只是**简单编码**，任何人都能解码看懂。
内容：算法类型、令牌类型
比如：`HS256`（HMAC-SHA256）

### 2. Payload 载荷
**Base64编码明文**
也是**肉眼能解码看懂的明文**，没有加密！
存业务数据：用户ID、过期时间、用户名等。

> 重点：
> **Header、Payload 都是公开明文，只是用 Base64 包装了一下，不是加密，不是哈希。**

### 3. Signature 签名
**HMAC-SHA256 哈希运算结果**
这一段**不是明文**，是：
`Header+Payload + 服务器私密密钥` 算出来的**哈希指纹**。
**不能反向解码、不能逆向推出密钥**。

---

# 二、完整 JWT 生成流程（登录时）
1. 服务器写好 **Header**（指定算法 HS256）
2. 服务器写好 **Payload**（用户ID、过期时间等）
3. 把 Header、Payload 分别做 **Base64 编码**
4. 拼接：`Base64(Header) + . + Base64(Payload)`
5. 用服务器**唯一私密密钥 SECRET_KEY**
   对上面拼接字符串做 **HMAC-SHA256 哈希**
   得到 **Signature 签名**
6. 把三部分用点拼接：
   ```
   Base64头.Base64载荷.哈希签名
   ```
7. **把完整这串 JWT 发给前端/浏览器**
👉 服务器**不存 Token**，只死守 **SECRET_KEY**

---

# 三、完整 JWT 验证流程（每次接口请求）
1. 客户端每次请求，带上完整 JWT 三段字符串
2. 服务器把 JWT 按 `.` 拆成三部分：
   - part1 = Header
   - part2 = Payload
   - part3 = 客户端带过来的 Signature（别人给的哈希结果）
3. 服务器**不取、不信 part3**，自己重新算：
   - 拿 `part1 + . + part2`
   - 用自己本地**私密密钥**
   - 再跑一次 HMAC-SHA256，算出**全新的哈希签名**
4. 对比：
   - 服务器自己算的新签名
   - VS 客户端传过来的第三段签名
5. 两种结果：
   - 相等：内容没被改、签名没被改，合法通行
   - 不相等：篡改过 Header / Payload / 随便改了签名，直接 401 拒绝
6. 额外再校验：Payload 里的**过期时间**是否已过期

---

# 四、关键总结（记这几句就够）
1. **Header、Payload**：
   Base64 明文，**任何人都能解码查看**，不存敏感密码！
2. **Signature**：
   是**带服务器密钥的哈希结果**，不可逆、不能伪造。
3. 服务器**不存任何 Token**，只存密钥；
   验证不靠查表比对，靠**原地重新算哈希做比对**。
4. 只要改 Header 或 Payload 任意一个字符，
   重新算出的哈希立刻大变，和原签名对不上，直接拦截。

---

# 五、极简一句话版
JWT 前两段是**包装过的公开明文**，第三段是**密钥算出来的哈希指纹**；
验证就是：服务器拿前两段+自己密钥**重算一遍哈希**，和第三段对比，一致就合法，不一致就是篡改。
