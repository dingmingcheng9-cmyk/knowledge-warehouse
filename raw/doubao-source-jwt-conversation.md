# source 简单解释
## 一、Linux/Shell 里的 `source`
**作用**：在**当前终端进程**里，执行脚本文件，不新建子进程。

### 语法
```bash
source 文件名
# 简写（常用）
. 文件名
```

### 核心特点
1. **不开启新进程**：脚本里改环境变量、切换目录，**会直接影响当前终端**。
2. 常用于：
   - 刷新环境变量：`source ~/.bashrc`
   - 激活虚拟环境：`source venv/bin/activate`
3. 对比 `bash 文件名` / `./文件名`：会**新建子进程**，子进程里改的东西，退出了就没了。

## 二、JavaScript 的 `source`
前端构建工具（Vite/Webpack）的 `source map`（源代码映射），把编译后代码映射回源码，方便调试。

## 三、日常用语 "source"
- 就是"来源"、"源头"
- 源代码、数据来源、信息来源

## 一句话：告诉当前终端"用我指定的 Python 环境"

| 部分 | 含义 |
|------|------|
| `source` | 在当前终端进程执行，不新建子进程 |

- `PATH` 被修改：虚拟环境的 `bin/` 优先于系统路径

- `pip install` → 包装进虚拟环境，不影响系统

### 激活 vs 不激活对比

| | 不激活 | 激活后 |
|---|---|---|
| `python` | 系统默认 Python | 虚拟环境里的 Python |

| 项目隔离 | ❌ 互相污染 | ✅ 每个项目独立 |

## 密码哈希的完整流程

### 注册时
```
用户输入密码 "abc123"
    ↓
哈希算法处理 → "$2b$12$LJ3m...9Xy"（一串乱码，长度固定）
    ↓
存入数据库的 password_hash 字段
```

### 登录时
```
用户输入密码 "abc123"
    ↓
去数据库找到对应用户
    ↓
从数据库取出 password_hash
    ↓
验证算法：输入的密码 vs 取出的哈希
    ↓
匹配 → 登录成功    不匹配 → 登录失败
```

### 关键区别

| | 加密 | 哈希 |
|---|---|---|
| 方向性 | 可逆（能解密） | 不可逆（不能还原） |
| 长度 | 与原文有关 | 固定长度 |
| 密码场景 | ❌ 不用 | ✅ 就用这个 |
| 例子 | AES、RSA | bcrypt、SHA-256 |

### 为什么哈希就够了

**服务器不需要知道你的原始密码**，它只需要：
1. 注册时：把你的密码变成哈希存起来
2. 登录时：验证你输入的密码能不能哈希成存的那个值

即使数据库被拖走，黑客拿到的是一堆哈希值，不是原始密码。

### 第 8 轮 — AI

先给你**核心结论**：

**哈希算法完全暴露也没关系，这正是密码哈希的安全所在。** 如果哈希算法需要保密才能安全，这个系统就是脆弱的设计。

## 为什么算法暴露也不怕

### 1. 哈希的"单向性"

算法公开，但只能正向计算，不能反向还原。

```
明文 → 哈希   ✅（很快）
哈希 → 明文   ❌（理论上不可行）
```

### 2. 暴力破解唯一方式：枚举

黑客如果拿到哈希值，唯一的破解方式就是把常见密码一个一个试：
- "123456" → 哈希
- "password" → 哈希
- 用彩虹表（预计算好的密码→哈希对照表）

### 3. 盐（Salt）彻底废掉彩虹表

每个用户的密码后面都拼了一段**随机字符串**（盐），然后才哈希。

```
用户 A 的密码: "abc123" + 随机盐 "A7x9" → 哈希
用户 B 的密码: "abc123" + 随机盐 "K3m2" → 完全不同的哈希
```

- 即使两个用户密码相同，哈希值完全不同
- 彩虹表彻底失效（因为盐是随机的，没法预先计算）

### 4. bcrypt 自身就带盐

bcrypt 哈希已经内嵌了随机盐，不需要手动管理盐。

```
$2b$12$LJ3m...9Xy
├─ $2b$ → bcrypt 版本
├─ 12   → 工作因子（2^12 轮迭代）
└─ 盐 + 哈希（自动生成和管理）
```

## 核心答案："慢"是故意的，而且慢得有策略

### 为什么密码哈希要故意"慢"

bcrypt 的工作因子（cost factor）决定了哈希计算的速度：
- cost=12：计算一次约 100ms
- cost=4：计算一次约 1ms

故意设慢的**唯一目的**：让黑客暴力破解的成本**指数级上升**。

### 为什么用户登录不觉得慢

**用户体验 vs 黑客成本：一次 vs 万亿次**

| | 用户登录 | 黑客破解 |
|---|---|---|
| 计算次数 | 1 次 | 数十亿次（常见密码字典） |
| 耗时 | ～100ms（几乎无感） | 100ms × 10亿 = 1亿秒 ≈ 3.17年 |
| 感受 | 瞬间完成 | 根本等不起 |

### 一句话总结

**用户只算 1 次，黑客要算 N 次。用户等 100ms 无所谓，黑客等不起这个时间。**

## 为什么每次 Token 不一样

**因为 Token 里包含了生成时间 `iat`（issued at），而每次生成的毫秒时间都不一样。**

```
Token = base64(header).base64(payload).签名
                        ↑
                    payload 里有：
                    - sub: 用户 ID
                    - exp: 过期时间
                    - iat: Token 生成时间（每次都不同）
```

## Token 的临时性（过期时间）

```
access_token_expire_minutes = 30
                ↓
Token 30 分钟后自动过期
                ↓
过期后：
- 浏览器再用这个 Token 请求 → 后端返回 401
- 前端检测到 401 → 提示用户重新登录
```

## 一张表看懂

| 场景 | Token 一样吗 | 说明 |
|------|-------------|------|
| 同一用户连续登录两次 | ❌ 不一样 | iat 不同，签名结果不同 |
| 重新登录 | ✅ 拿到新 Token，旧 Token 过期作废 |
| 过期后 | ❌ 不能再用 | 后端验签失败，返回 401 |

## JWT 配置代码逐行拆解

```python
SECRET_KEY = "my-super-secret-key-change-in-production"
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_MINUTES = 30

pwd_context = CryptContext(schemes=["bcrypt"])
```

### 各行含义

| 代码 | 通俗解释 | 作用 |
|------|---------|------|
| `SECRET_KEY = "..."` | 你的私人印章 | 签 Token 用的唯一密码 |
| `ALGORITHM = "HS256"` | 你选择用什么签法 | HMAC-SHA256 签名算法 |
| `ACCESS_TOKEN_EXPIRE_MINUTES = 30` | Token 有效期 | 30 分钟后 Token 作废 |

```python
def hash_password(password: str) -> str:    # 注册时用
    return pwd_context.hash(password)

def verify_password(plain_password: str, hashed_password: str) -> bool:  # 登录时用
    return pwd_context.verify(plain_password, hashed_password)
```

### 密码哈希函数

| 函数 | 什么时候用 | 做了什么 |
|------|-----------|---------|
| `hash_password` | 用户注册 | 明文密码 → bcrypt 哈希 |
| `verify_password` | 用户登录 | 对比输入的密码和数据库里的哈希 |

```python
def create_access_token(user_id: int) -> str:  # 登录成功时调用
    expire = datetime.now(timezone.utc) + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
    payload = {"sub": str(user_id), "exp": expire}
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)
```

### Token 生成函数

```
登录成功时：
    ↓
1. 计算过期时间 = 现在 + 30 分钟
2. 组装 payload = {"sub": "用户ID", "exp": 过期时间}
3. 用 SECRET_KEY 和 HS256 给 payload 签名
4. 返回完整的 JWT Token 字符串
```

### 第 32 轮 — AI

我给你把这个**灵魂疑问**彻底讲透，一句话先点破：

## Token 和签名是两回事

### 比喻：一张身份证

```
Token（令牌） = 身份证本身
签名          = 身份证上的防伪标记（公安部盖章）
```

| | 身份证 | JWT Token |
|---|---|---|
| 主体内容 | 姓名、照片、身份证号 | user_id、过期时间 |
| 防伪标记 | 公安部盖章、全息图 | 签名（SECRET_KEY 生成） |
| 谁能伪造 | 只有公安部 | 只有持有 SECRET_KEY 的人 |

### 为什么要签名

假设没有签名，普通用户完全能看到 Token 内容是 base64 编码：

```python
# Token payload 部分只是 base64 编码，不是加密！
import base64
payload = base64.b64decode("eyJzdWIiOiIxIiwiZXhwIjoxNjgwMDB9")
print(payload)  # {"sub": "1", "exp": 168000}
```

如果不对 payload 签名，用户可以：
1. 解码 Token
2. 把 `"sub": "1"` 改成 `"sub": "2"`
3. 重新编码
4. 拿着伪造的 Token 访问别人的数据

**签名阻止了这个行为**：Token 被修改后，签名验证不通过，直接 401。

### 一句话总结

签名解决了**"你怎么证明这个 Token 是你服务器发的"**这个问题。

### 第 34 轮 — AI

对，你总结得**精准到满分**，我帮你再精炼、固化成标准答案：

### 标准回答

**签名的作用就是「防篡改验证」。**

```
服务器生成 Token:
    payload + SECRET_KEY → 签名 → 完整 Token

服务器验证 Token:
    Token → 拆开 → payload + 签名
                ↓
    用 SECRET_KEY 重新算一遍签名
                ↓
    两个签名比对：
    ├─ 一样 ✅ → Token 未被修改，通过
    └─ 不一样 ❌ → Token 被篡改，拒绝
```

### 为什么签名的本质是哈希

```
payload + SECRET_KEY → HMAC-SHA256 → 固定长度的签名
                                        ↑
                                   这本身就是哈希运算
                                      （带密钥的哈希）
```

### 三层总结

| 层级 | 一句话 |
|------|--------|
| 入门 | Token 是通行证，签名是防伪标记 |
| 进阶 | 签名 = 哈希(payload + SECRET_KEY) |
| 高手 | **签名就是把哈希运算应用在 Token 防伪上** |

### 第 40 轮 — AI

**你问到了最核心的技术点！答案是：对！完全就是哈希算法！**

## Token 签名本质上就是哈希

```
HMAC-SHA256(payload, SECRET_KEY)
        ↓
    哈希运算
        ↓
    固定长度签名
```

### 完整 Token 结构

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIiwiZXhwIjoxNjgwMDB9.zV8sfjV5w...
├────────header────────┼───────payload─────────┼───────signature───────┤
       base64                base64               HMAC-SHA256 结果
                                                   （不可逆，固定长度）
```

### 签名的"不可逆性"就是哈希的单向性

```
payload + SECRET_KEY → 签名   ✅（给定输入，得到确定输出）

签名 → 反推出 SECRET_KEY     ❌（哈希单向性，理论上不可能）
```

### 总结：把之前学的密码学知识串联起来了

```
密码哈希：   明文密码 + 盐  → 哈希  → 存数据库
Token 签名： payload + 密钥  → 哈希  → 签名部分
```

**两次都是哈希运算，只是应用场景不同。**

### 第 42 轮 — AI

先给你**核心结论**：

## Token 验证全部在服务器内部完成

### 验证流程

```
请求到达服务器
    ↓
1. 从 Header 取出 Token：Authorization: Bearer eyJ...
    ↓
2. 拆 Token：用 "." 分成三部分
   - header    → base64 解码 → {"alg": "HS256"}
   - payload   → base64 解码 → {"sub": "1", "exp": 168000}
   - signature → 拿到原签名
    ↓
3. 验签名：用 SECRET_KEY 重新算一遍签名
   - 新签名 = HMAC-SHA256(header + "." + payload, SECRET_KEY)
   - 新签名 == 原签名？→ ✅ 通过 / ❌ 拒绝
    ↓
4. 验过期：exp > 当前时间？→ ✅ 通过 / ❌ 401
    ↓
5. 查用户：sub = 1 → 从数据库查出用户 → 返回数据
```

### 客户端做不到的事

```
客户端做不到任何跟签名有关的事，因为：
❌ 不知道 SECRET_KEY
❌ 不能生成有效签名
❌ 不能修改 Token 内容（改了签名就失效）
✅ 只能乖乖拿着 Token 请求
```
